# Platform Metrics Snapshot Plan

版本：v0.1  
日期：2026-07-03  
范围：ClipFlow 的月度平台数据快照、Dashboard 增长展示、月度复盘补录流程

## 1. 结论

平台播放量、点赞、评论、收藏等数据第一版不做实时同步，也不假设抖音或其他平台一定提供稳定接口。

产品上把它定义为：

> 月度平台数据快照：用户在月度复盘前上传或录入平台截图，系统整理成可回溯的结构化数据。

它的价值是月度归档和复盘，不是实时运营监控。

## 2. 为什么这样做

当前 `00_state` 已经能稳定记录制作数据：

- 做了多少条视频
- 每条视频多长
- 制作耗时多少
- 文件大小多少
- 是否发布
- 视频、封面、脚本、日志路径

但平台表现数据有两个问题：

- 不一定有稳定 API。
- 如果没有固定采样时间，零散看到的数字很难用于复盘。

所以第一版采用“月末人工快照”的方式，让数据有固定时间点和原始证据。

## 3. 数据模型

新增平台指标快照表：

```text
platform-metrics-snapshots
```

字段：

| 字段 | 含义 |
| --- | --- |
| `snapshot_id` | 快照唯一 ID |
| `content_id` | 关联 `00_state/content-ledger.csv` 的内容 ID |
| `platform` | 平台，例如 `douyin` |
| `snapshot_date` | 截图或录入日期 |
| `snapshot_type` | `monthly`、`t_plus_1`、`t_plus_7` |
| `views` | 播放量 |
| `likes` | 点赞数 |
| `comments` | 评论数 |
| `favorites` | 收藏数 |
| `shares` | 分享数 |
| `screenshot_path` | 原始截图路径 |
| `ocr_status` | `pending`、`parsed`、`verified` |
| `notes` | 人工备注 |

MVP 默认只要求 `monthly` 快照。`T+1 / T+7` 是后续增强，不作为第一版强制项。

## 4. 月末采集流程

1. 用户进入“月度平台快照”页面。
2. 系统列出本月已发布视频。
3. 用户按视频上传平台截图，或手动录入平台数据。
4. 系统尝试 OCR 识别截图数据。
5. 用户在校对界面确认或修改结果。
6. 系统保存结构化快照。
7. Dashboard 和月度汇总读取快照展示增长表现。

第一版可以先做手动录入表单，不强依赖 OCR。OCR 是增强能力，不能阻塞主流程。

## 5. Dashboard 展示口径

Dashboard 默认展示本月数据。

顶部增长指标：

- 本月播放量快照合计
- 本月点赞合计
- 本月评论合计
- 本月收藏合计
- 已补平台数据的视频数
- 平台数据缺失的视频数

同时保留生产指标：

- 本月制作视频数
- 本月发布视频数
- 本月视频总时长
- 本月制作总时长
- 本月导出文件总大小

页面必须标注：

```text
平台数据来自手动月度快照
```

缺失平台快照时，展示 `待录入平台快照`，不能用 `0` 代替缺失值。

## 6. 月度汇总口径

月度汇总读取两类数据：

- 制作数据：`00_state/production-stats.csv`
- 平台数据：`platform-metrics-snapshots`

月度汇总展示：

- 本月视频列表
- 每条视频的制作成本
- 每条视频的播放量和互动数
- 制作时长与播放表现的对照
- 缺失平台快照的视频提醒

月度复盘的核心问题：

- 哪些视频产出成本高但表现普通？
- 哪些视频制作很轻但表现不错？
- 哪些主题、封面或栏目值得延续？
- 哪些视频缺平台快照，需要补录？

## 7. 与封面画廊的关系

封面画廊继续作为一级模块，收集两类素材：

- `generated`：每次视频生成的封面图。
- `reference`：用户从外部截图收藏的好看封面。

平台快照数据可以和封面画廊形成后续分析：

- 哪些封面风格对应的视频表现更好。
- 哪些参考封面被用于生成实际封面。
- 哪些栏目适合固定封面模板。

MVP 只记录关联，不做复杂归因分析。

## 8. 产品完整性检查

这个方案补齐的是“生产数据 -> 平台反馈 -> 复盘判断”的最后一环。

当前产品闭环：

```text
Dashboard
-> 创建视频
-> 生成脚本 / 上传视频 / 封面 / 剪辑 / 归档
-> 00_state 记录制作数据
-> 月末平台快照补录
-> Dashboard / 月度汇总展示增长表现
-> 反哺选题、封面风格、制作节奏
```

从产品完整性看，它覆盖了四个必要面：

| 模块 | 现在是否覆盖 | 说明 |
| --- | --- | --- |
| 创作入口 | 已覆盖 | `/create` 承载视频创作工作流 |
| 生产数据 | 已覆盖 | `00_state` 记录时长、耗时、文件、发布状态 |
| 风格资产 | 已覆盖方向 | `gallery` 管理生成封面和参考封面 |
| 平台表现 | 本计划补齐 | 用月度快照记录播放和互动 |

暂不做的内容：

- 实时播放量监控。
- 平台 API 自动抓取。
- 每日自动定时同步。
- 复杂的封面表现归因。
- 多平台账号管理。

这些不影响 MVP 完整性。第一版只要能完成“创建、归档、月末补平台数据、回看复盘”，产品闭环就是成立的。

## 9. 推荐实施顺序

第一阶段：文档和样例数据。

- 新增 `platform-metrics-snapshots` 样例数据。
- Dashboard 用样例数据展示平台快照。
- 月度汇总展示缺失快照提醒。

第二阶段：手动录入。

- 增加平台快照录入页面。
- 支持按视频录入播放量、点赞、评论、收藏、分享。
- 支持上传截图路径或截图文件引用。

第三阶段：OCR 辅助。

- 上传截图后尝试识别数字。
- 用户确认后才入库。
- `ocr_status` 标记识别和校对状态。

第四阶段：轻量趋势。

- 可选增加 `T+1 / T+7 / monthly` 三种快照。
- Dashboard 展示简单趋势，不做实时监控。

## 10. 验收标准

- Dashboard 能区分制作数据和平台快照数据。
- 平台数据缺失时显示缺失状态，不显示为 0。
- 月度汇总能显示哪些视频已补平台快照。
- 每条平台快照都能追溯到截图路径。
- 第一版不依赖抖音 API。
- 数据结构允许未来增加自动抓取来源。
